## 结果

最终 12/12 完成且页面 oracle 通过，JS 与纯工具分别 6/6。没有重复成功查询，没有不必要的失败重试，没有错误最终字段或错误勾选状态；页面无效操作与基于 oracle 的误报完成都为 0。两次 retry 的请求均为「蓝牙耳机、充电器、充电器、数据线」。这不代表摘要中的所有过程描述都正确，见下文。

| JS 指标 | 原始基线 | 优化后 |
| --- | ---: | ---: |
| 成功 | 6/6 | 6/6 |
| 平均耗时 | 20.06 s | 14.46 s（-27.9%） |
| 平均非模型耗时 | 11.17 s | 6.34 s（-43.2%） |
| 平均规划轮数 | 6.0 | 5.5 |
| 平均总 token | 30,574 | 29,910（-2.2%） |
| 脚本错误 | 3 | 0 |
| 条件等待超时 | 1 | 0 |
| 固定 sleep | 51 次 / 24.151 s | 15 次 / 6.015 s |
| query | 90 次 | 38 次 |
| 接受的设备变更 | 59 | 58 |

模型实际完成了 16 次 waitAny、23 次 setText、4 次 setChecked；全部 27 段脚本都使用了显式 id 构造器。JS 的 58 次设备变更等于这组任务的最低需要数量，原始基线多一次输入。宿主内部的只读等待/验证采样仍计入耗时、任务读取上限；减少高层 query 调用不能解释为底层总读屏一定同比减少。

当前同轮 JS 相对纯工具：平均耗时减少约 38.3%，平均总 token 少约 67.1%。这是当前形态的比较；不能把这两项都算作本次 SDK 改动带来的收益。

## 未改善与剩余问题

- **纯工具组没有性能提升。** 平均耗时 22.11 → 23.45 s，token 81,217 → 90,882。规划轮数 13.33 → 15；接受操作 58 → 67。轨迹显示 retry/工具第 1 次多了 6 次输入框聚焦点击，batch/工具第 2 次多了 3 次聚焦点击；没有重复业务查询。该组的模型决策仍存在冗余操作。
- **条件语义仍取决于模型。** 部分脚本仍以永久结果区域的存在代表结果就绪，再用短 sleep 补偿。waitAny 能清晰表达多分支，但不能自动理解业务上“成功”的含义。后续可补充文本变化等只读等待，继续用不同页面验证迁移性。
- **过程摘要仍可能失真。** retry/工具第 2 次的最终字段和请求序列均正确，但摘要错误地说没有失败或重试；真实日志明确包含一次失败与重试。batch/JS 第 1 次摘要还过度解释了首次读取时机。oracle 验证真实操作与最终状态，不保证自然语言过程说明完全正确；报告的 falseCompletion 仅指 COMPLETED 但页面 oracle 未通过。
- **token 改善很小。** JS 平均总 token 仅下降约 2%，新增 SDK 说明和结构化返回也有上下文成本。工具结果与 recentActions 去重仍是下一阶段候选，尚未改动、没有宣称收益。

## 首轮失败和修复

本轮实际新跑了两组完整 12 次，未删除失败样本。首轮版本 01c3b86 为 9/12：严格条件解析遇到简写时直接在模型决策阶段抛错，未进入动作校验反馈。一次页面已经完成也因此不能正常 finish。修复为规范化无歧义简写，并把其余参数错误作为受次数限制的本地反馈，无设备输入、无自动重放。

另补充了不可变选择器及超时范围说明、JS 本地错误的部分执行摘要、旧引擎缺少 rawText 时的前置拒绝。真实清空测试发现 Android 的 getText 在空输入时可能返回 hint，最终 rawText 使用 isShowingHintText 区分空值，状态值也参与快照指纹。
