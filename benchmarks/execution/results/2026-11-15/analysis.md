# 结论与运行轨迹审阅

本次 12 次真机运行中，两组均 6/6 完成，查询顺序、次数、字段与最终状态全部符合目标，摘要人工核对也正确。JS 平均模型轮数降低 **55%**，总 token 降低 **62.4%**，平均耗时仅降低 **9.3%**。这些结果来自 Pixel 6 / Android 17、用户当前配置的 `deepseek-flash`、关闭思考模式，以及三个原生控件流程；每个任务每种模式只有两次样本。

## 哪些流程获益

- **跨页填写**：15.43 s → 10.54 s，模型轮数 10 → 4，平均 token 52,940 → 18,618。脚本在页面边界返回观察，再批量填写下一页，减少了模型往返。
- **批量查询回填**：21.40 s → 20.84 s，轮数 14 → 6.5，token 84,817 → 33,018。token 收益明显，平均速度变化很小。
- **失败后局部重试**：29.52 s → 28.80 s，轮数 16 → 7.5，token 105,894 → 40,086。JS 把操作合并后仍需要模型处理错误分支和调整等待，因此没有获得同等幅度的时间收益。

## 失败步骤与恢复

最终成功不代表中途没有错误：

- JS 一共出现 **3 次脚本错误**：两次选择器没有匹配到目标，一次试图操作未启用控件。均在操作前被校验拦截，没有重复成功查询或多点一次重试；模型观察实际状态后继续完成。
- 两次定位错误来自把 `#benchmark_query` 或完整资源 ID 直接作为字符串参数。当前字符串约定是“精确匹配文字”，资源 ID 应写 `{resourceId: ...}`。这是当前模型使用接口的真实失误，没有为本次评估新增 CSS/ID 隐式兼容来掩盖它。
- 纯工具有 **1 次页面指纹过期拒绝**，操作未执行，重新观察后恢复。[第 8 次轨迹](traces/08-wizard-tools_only.jsonl) 可查看错误及后续步骤。
- JS 接受了 59 个实际变更，工具组 58 个；差异是一处重复设置输入文本。查询、校验和最终值均满足约束，无重复成功查询。页面 oracle 记录的无效关键词/校验点击均为零。

相关 JS 错误轨迹：[第 4 次](traces/04-retry-script_only.jsonl)、[第 11 次](traces/11-batch-script_only.jsonl)。

## 为什么减少一半轮数，速度只快一点

模型 HTTP 总耗时从 88.59 s 减到 53.38 s，但 JS 的设备操作、轮询与其他耗时从 44.09 s 增到 66.99 s，抵消了大部分节省。

两段明显的额外等待：

1. 第 4 次运行，校验通过后的结果仍包含“数据线”，脚本却在循环等文字不再包含“数据线”，直到循环耗尽。最后一个脚本段约 10.44 s；整次运行的 `sleep` 合计约 10.43 s。
2. 第 11 次运行也使用了类似条件，最后一段约 9.97 s；整次 `sleep` 合计约 9.52 s。该次 JS 用时 **26.50 s**，比同一配对中的纯工具 **20.27 s** 更慢。

另有一次错误分支等成功条件 8 秒直到超时，才由模型继续判断。它们是脚本生成的等待条件问题，数据不能支持“QuickJS 计算慢导致整个流程慢”的判断。本次没有测通用 CPU 吞吐，也不据此对引擎计算性能排名。

## Token 与费用不能混为一谈

| 六次任务合计 | 纯工具 | JS |
| --- | ---: | ---: |
| 输入 token | 480,258 | 175,736 |
| 输出 token | 7,042 | 7,710 |
| 服务商报告的缓存命中输入 token | 279,040 | 105,984 |
| 总 token | 487,300 | 183,446 |

JS 的输入显著减少，但生成代码使输出略有增加。不同 token 单价与缓存计费会改变费用，因此 **62.4% 是总 token 降幅，不能直接作为费用降幅**。两组未发生模型网络错误或独立完成复核；本次 HTTP 请求数与规划轮数相同。

## 对当前产品的判断

继续保留 AUTO 的混合能力：可预测的重复步骤用短 JS，页面边界或不确定状态返回模型检查。当前数据支持“JS 能显著减少上下文与模型往返”，不支持“一律强制 JS 会明显更快或成功率更高”。

后续优化应优先解决选择器约定和条件等待的易用性，让模型少写手工 sleep/字符串轮询；再用同一任务集重测，并加入第三方 App、自绘界面、跨 App 和更长任务。本次未在跑完后修改 API 或挑选重跑样本来改善数据。
